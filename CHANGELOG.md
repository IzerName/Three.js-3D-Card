## [0.1.1] — 2026-10-14

### Добавлено

* **Однофайловая сборка `threejs-3d-card.js` в корне репозитория** — её ставит
  HACS: `hacs.json` → `"filename": "threejs-3d-card.js"`, HACS ищет файл в корне
  репозитория и скачивает корневые `.js` (у нас он один). Внутри — three.js r160,
  загрузчики OBJ/MTL/glTF, ядро карточки и встроенные модели, около 911 КБ.
  После установки карточке на сервере больше ничего не нужно: ни `vendor/`, ни
  `src/`, ни `models/`.
* **Проверка однофайловой сборки на стенде** — `dev/probe-bundle.html`: загрузка
  как модуля, регистрация элементов, публикация API, three.js из бандла, ноль
  запросов к `vendor/`, `src/` и `models/`, отрисовка кадров, переподключение
  карточки. Бандл стенд отдаёт по `/bundle/threejs-3d-card.js`, прогон в
  headless Chrome — `node dev/probe-runner.mjs
  http://127.0.0.1:8099/dev/probe-bundle.html 25000`.
* **`test/bundle.test.js`** — проверяет бандл: нет относительных импортов,
  элементы регистрируются, `window.ThreeJS3DCard` публикуется с отметкой
  `bundled: true`, three.js поднимается из бандла (`api.loadThree()` →
  REVISION 160), встроенные модели доступны. Общая эмуляция DOM для
  `release.test.js` и `bundle.test.js` вынесена в `test/dom-stub.mjs`.

### Исправлено

* **Повторный `attachShadow`.** Когда Lovelace переподключал элемент, карточка
  падала с `NotSupportedError: Shadow root cannot be created on a host which
  already hosts a shadow tree`. Теневой корень теперь создаётся один раз и
  переиспользуется.

### Изменено

* **Импорты three.js и загрузчиков стали литеральными**: вместо вычисляемого URL
  библиотеки — `import("../../vendor/three.module.js")` в
  `src/core/three-loader.js` и такие же импорты загрузчиков OBJ/MTL/glTF в
  `src/core/geometry.js`. Так esbuild подставляет их внутрь однофайловой сборки,
  а в раскладке `dist/` те же пути работают по сети.
* **`dist/` — раскладка для стенда и ручной установки**, а не то, что ставит
  HACS: её отдаёт `npm run serve`, и она же уходит в архив
  `threejs-3d-card.zip`. Собирается по-прежнему без бандлера.
* **CI сверяет закоммиченное со сборкой**: `git diff --exit-code -- dist
  threejs-3d-card.js` — `dist/` и корневой бандл коммитятся вместе, и релизный
  workflow падает, если они разошлись с `src/` и `models/`.
* Тестов стало **101** (`npm test`): добавлены `test/bundle.test.js` и проверки
  раскладки для HACS в `test/publish.test.js`.

## [0.1.0] — 2025-10-13

Первая версия: одна карточка для всех 3D-сцен.

### Добавлено

* Карточка `custom:threejs-3d-card` — 3D-сцена на three.js с данными
  Home Assistant в реальном времени.
* **Модели как плагины.** Сцена описывается отдельным JS-файлом: `manifest`
  (паспорт, камера, окружение), `bindings` (привязки к сущностям), `params`
  (настройки внешнего вида), `create(ctx)` (построение сцены).
* **Редактор, строящийся из модели.** Форма привязок создаётся по описанию
  модели, устройства выбираются штатным `ha-entity-picker` с фильтром по
  домену, `device_class` и единице измерения. Ручной ввод `entity_id` не
  требуется.
* **Импорт внешних моделей.** Модель по URL (`/local/3d-models/my-model.js`)
  загружается прямо из редактора карточки, без пересборки и релиза.
* **Объектная модель из спецификации.** Готовая геометрия — OBJ + MTL или
  glTF/GLB — связывается с сущностями декларативно: цвет по состоянию и по
  числу, скрытие, подсветка светильников, вращение, открывание дверей и окон,
  текст состояния, клики по именованным объектам. Логика живёт в карточке
  (`object-model.js`, `object-rules.js`), модель остаётся данными.
* **Скилл `skills/threejs-3d-model`** — инструкция для агента: по словесной
  просьбе собирает спецификацию, обёртку-модуль и инструкцию по установке;
  в комплекте валидатор спецификации и рабочий пример.
* **`getStubConfig`** подбирает подходящие сущности по `device_class`,
  единице измерения и именам, чтобы новая карточка сразу показывала данные.
* **Модальное окно сущности**: состояние, атрибуты с переводом подписей,
  время изменения, кнопки управления для `switch`, `light` (яркость),
  `climate` (режим, температура), `cover`, `lock`, `button`, `script`,
  `automation` и переход в Home Assistant по `hass-more-info`.
* **Диагностика привязок** — панель в карточке: какие ключи заполнены, какие
  сущности не найдены или недоступны, что сообщила модель.
* **three.js в поставке** (`vendor/three.module.js`, r160) — работает без
  интернета; CDN используется только как резерв.
* **Бережное отношение к ресурсам**: один WebGL-контекст на карточку, пауза
  рендера вне экрана (`IntersectionObserver`), освобождение геометрий,
  материалов и текстур при удалении карточки, обработка
  `webglcontextlost`/`restored`, поддержка `prefers-reduced-motion`.
* **Модель `water-tank`** — бак чистой воды (перенесена из проекта
  water-tank-3d без изменений в геометрии и анимации).
* **Модель `production-room`** — производственное помещение (перенесена из
  проекта production-room-viewer).
* **Совместимость с прежними карточками**: конфигурации
  `custom:water-tank-card` и `custom:production-room-card` продолжают
  работать, включая плоские параметры в корне конфигурации.
* Стенд разработки `dev/harness.html` с демо-состояниями Home Assistant.
* Сборка `dist/` без сторонних бандлеров (`scripts/build.mjs`) и локальный
  HTTP-сервер (`scripts/serve.mjs`).
* **Раскладка `dist/`** (закоммичена): точка входа, `src/`, `models/` и
  `vendor/` — обычные ES-модули для стенда и ручной установки.
* Юнит- и интеграционные тесты (`npm test`), включая проверку раскладки релиза
  для HACS (`test/publish.test.js`).
* Документация: [docs/MODEL_API.md](docs/MODEL_API.md) — контракт модели,
  [docs/CONFIGURATION.md](docs/CONFIGURATION.md) — параметры карточки,
  [docs/HACS.md](docs/HACS.md) — публикация в HACS.

### Известные ограничения

* Модель `production-room` перенесена как адаптер и ещё не разложена на общие
  примитивы ядра.
* three.js r160 зафиксирован: смена версии требует проверки моделей.
* Установка через HACS проверена по структуре релиза; проверка на «чистом»
  Home Assistant выполняется перед публичным релизом.

### Исправлено в ходе проверки на реальном браузере

Проверки в headless-Chrome (`dev/probe.html`, `dev/probe-ext.html`,
`dev/probe-render.html`) выявили и позволили устранить:

* **Два WebGL-контекста на одном канвасе.** Карточка создавала свой рендерер,
  а затем модель — свой на том же канвасе; второй контекст молча не работал, и
  сцена после смены модели оставалась пустой. Введён `manifest.host:
  "external"`: для таких моделей карточка создаёт только канвас.
* **Потеря контекста при смене модели.** Движок цеха вызывал
  `renderer.dispose()` на общем рендерере, из-за чего следующая сцена не могла
  рисовать. Освобождение общего контекста отключено (`disposeRenderer`).
* **Сцена не строилась вообще.** `_rebuild()` не запускал повторное построение,
  а приход `hass` во время загрузки модели терялся. Построение стало
  перезапускаемым (`_bootAgain`), конфигурация и состояния больше не «залипают».
* **Падение редактора.** `_render()` вызывался из `connectedCallback` до
  `setConfig` и падал на `this._config.model`.
* **Внешние модели не кэшировались.** Повторный `resolve(url)` каждый раз
  скачивал файл заново; модель теперь доступна и по `manifest.id`, и по URL.
* **`ResizeObserver.observe` на объекте-обёртке** падал при подключении
  готового движка через адаптер — наблюдение ведётся за настоящим элементом.
* **`window.ThreeJS3DCard.THREE`** не был заполнен к моменту вызова `create()`;
  карточка загружает three.js сразу при подключении ресурса, а движок ждёт
  `threeReady`. Примеры и документация переведены на `ctx.THREE`.
* **Запуск тестов** переведён на изоляцию по файлам: глобальные заглушки DOM
  больше не конфликтуют, а падение одного файла не мешает остальным.
