# Объектные модели: декларативный формат `createObjectModel`

Документ для разработчика: как устроен наш формат описания 3D-модели данными
(JSON + обёртка-модуль), как работает движок правил и чем это отличается от
floor3d-card.

Связанные документы:

* `skills/threejs-3d-model/reference/SPEC.md` — полный справочник полей
  спецификации (первоисточник; здесь — только то, что нужно понимать код).
* `docs/MODEL_API.md` — общий контракт модели карточки (`create(ctx)`,
  `attach(ctx)`, `ctx`, `host: "external"`).
* `docs/OBJECT_NAMES.md` — как получить имена объектов модели.
* `src/core/object-model.js`, `src/core/object-rules.js`, `src/core/geometry.js`
  — реализация.

---

## 1. Где это место в архитектуре

Модель для карточки можно сделать двумя способами.

| Способ | Что пишет автор | Где логика |
|---|---|---|
| **Модуль модели** (`docs/MODEL_API.md`) | `export default { manifest, create(ctx) {…} }` — код на three.js | в модели |
| **Объектная модель** (этот документ) | JSON-спецификация + обёртка на 3–8 строк вокруг `createObjectModel(spec)` | в карточке (`object-rules.js`) |

Объектная модель — это «данные вместо кода»: спецификация говорит, **откуда
взять геометрию** и **какая сущность Home Assistant что делает с каким
именованным объектом**; всё остальное (сглаживание, источники света, спрайты,
поворот дверей) делает универсальный движок правил.

```
config/www/3d/
├─ house-model.json   ← спецификация (данные)
├─ house-model.js     ← обёртка: export default createObjectModel(spec)
├─ house.obj          ← геометрия
└─ house.mtl          ← материалы (необязательно)
```

```js
// /local/3d/house-model.js
// Фабрику берём из глобального API карточки: путь к её модулям зависит от
// каталога установки (/hacsfiles/<имя-репозитория>/… при HACS,
// /local/<любая-папка>/… вручную), поэтому импорт с жёстким путём ненадёжен.
const { createObjectModel } = window.ThreeJS3DCard;

const spec = await fetch("/local/3d/house-model.json").then((r) => r.json());
export default createObjectModel(spec);
```

```yaml
# конфигурация карточки
type: custom:threejs-3d-card
model: /local/3d/house-model.js
entities:
  light.kitchen: light.kitchen                 # ключ = entity из спецификации
  binary_sensor.front_door: binary_sensor.front_door
```

`entities` — обязательная часть работы: `entity` в привязке это **ключ**, а не
готовый `entity_id`. Пока пользователь не выбрал сущность (в редакторе или в
YAML), движок не получает состояний, и правила молчат
(`src/core/bindings.js`, `normalizeConfig`, `bindingView()` в `scene.js`).

## 2. `createObjectModel(def)`

`def` — объект спецификации. Функция возвращает описание модели для реестра
карточки (`bindings` для редактора, `params`, `defaults` и `create(ctx)`).

| Поле `def` | Обяз. | Что делает |
|---|---|---|
| `manifest` | **да** (`manifest.id`) | Паспорт: `id`, `name`, `description`, `camera`, `environment`, `size`. По умолчанию добавляется `apiVersion: 1`. `host` у объектной модели указывать **не нужно** — см. §6. |
| `source` | **да** | Источник геометрии: `url`, `format` (`obj`/`gltf`; `.glb` = `gltf`), `mtl`, `scale`, `fitSize`, `center`, `ground`, `dracoPath`, `normalize`. |
| `bindings` | нет | Массив привязок «сущность → объекты → действия». Ядро формата, см. §4. |
| `groups` | нет | Именованные наборы объектов: `{ "lights": ["Lamp_1", "/^Lamp_/"] }`; в `target` — `@lights`. |
| `entityConfig` | нет | Переопределение полей привязок для редактора карточки (`name`, `group`, `hint`, `domain`, `kind`, `overrides`). |
| `params` | нет | Настройки модели, которые пользователь меняет в редакторе (типы: `number`, `range`, `boolean`, `text`, `theme-color`, `color`, `select`). |
| `defaults` | нет | Значения конфигурации карточки по умолчанию (по умолчанию — заголовок из `manifest.name`, `show_hud: true`, `height: 460`). |
| `options` | нет | Зарезервировано, в текущей реализации не читается. |

Что происходит при построении сцены (`create(ctx)` в `object-model.js`):

1. `normalizeSource(def.source, ctx.asset("."))` — разрешение относительных
   путей и формата (формат угадывается по расширению; для `blob:`-URL его
   задают явно);
2. `loadGeometry(ctx, source)` — загрузка через OBJ+MTL или GLTFLoader, кэш по
   ключу `формат|url|mtl` и **клон** дерева на каждую сцену
   (`src/core/geometry.js`);
3. `centerAndScale()` — центрирование по X/Z, установка на `y = 0`, `scale` или
   `fitSize` (по умолчанию включено; отключается `center: false`,
   `ground: false`, `normalize: false`);
4. модель заворачивается в `THREE.Group` с именем `manifest.id`,
   считается `Box3` (карточка ставит камеру по габаритам);
5. `createRuleEngine(def, ctx, group)` — разбор привязок и подготовка правил
   (именно здесь создаются источники света и спрайты);
6. объекты, попавшие в `target`, помечаются для клика (`tagObjectByTarget` →
   `ctx.tag`) — клик по объекту открывает сущность в карточке.

Возвращаемый handle (то, чем пользуется карточка):

| Поле | Назначение |
|---|---|
| `root` | `THREE.Group` для сцены карточки. |
| `external` | `false`: сцену рисует рендерер карточки, а `frame(dt)` только обновляет правила. |
| `applyState(key, info)` / `applyStates(view)` | Приём состояний: `ruleEngine.setEntity(key, info)` под каждую привязку. |
| `frame(dt)` | Покадровый вызов: пересчёт «грязных» правил и применение действий. |
| `resize()` | Ничего не делает (камера настраивается по габаритам). |
| `dispose()` | Освобождение правил (спрайты, источники света) и собственных копий материалов. |
| `ruleEngine` | Доступ к движку: `objectNames()`, `describe()` — для тестов и диагностики. |
| `bounds` | `THREE.Box3` модели. |

## 3. Проверка спецификации

```bash
node skills/threejs-3d-model/scripts/validate-model.mjs путь/к/house-model.json
```

Валидатор ловит опечатки в названиях действий, неизвестные поля, пустые
`target`/`entity`, расхождения `entityConfig` с `bindings`, ошибки в `door`
(`slide` вместе с `degrees` и т. п.). Код возврата — 1 при ошибках, поэтому
команда годится для CI.

## 4. Движок правил (`src/core/object-rules.js`)

### 4.1 Адресация объектов (`target`)

| Форма | Пример | Что находит |
|---|---|---|
| Точное имя | `"Lamp_Kitchen"` | Один объект; регистр не важен (в индексе есть алиасы в нижнем регистре). |
| Массив | `["Lamp_1", "Lamp_2"]` | Несколько объектов; на каждый создаётся своё правило. |
| Шаблон | `"Lamp_*"`, `"Door_?"` | Все объекты по маске (`*` — любые символы, `?` — один). |
| Регулярка | `"/^Lamp_/"` | Все объекты, чьё имя подходит под выражение (без флагов, регистр не важен). |
| Группа | `"@lights"` | Объекты из блока `groups` спецификации. |

Детали реализации:

* индекс строится обходом всего дерева (`traverse`), поэтому объект можно
  адресовать на любой глубине;
* при дубликате имени в индексе остаётся **последний** найденный объект, а
  маски и регулярки вернут все совпадения — имена должны быть уникальны;
* группы разворачиваются **до** привязок, поэтому `@группа` в `target` работает;
* ненайденный `target` — это не ошибка загрузки: правило не создаётся, а в
  диагностику карточки уходит предупреждение
  `объект «…» не найден в модели (привязка …)`.

### 4.2 Действия: краткая и полная запись

```json
{ "entity": "light.kitchen", "target": "Lamp_Kitchen",
  "colors": { "on": "#ffd9a0", "off": "#3a3a3a" }, "light": { "lumens": 800 } }
```

```json
{ "entity": "light.kitchen", "target": "Lamp_Kitchen",
  "actions": [
    { "action": "color", "colors": { "on": "#ffd9a0", "off": "#3a3a3a" } },
    { "action": "light", "lumens": 800 }
  ] }
```

Записи эквивалентны: краткие ключи (`colors`/`color`, `hide`, `light`,
`rotate`, `door`, `text`) нормализуются в массив действий. Одна привязка может
содержать несколько действий, и все они применяются к каждому объекту из
`target`.

Сглаживание задаётся полем `rate` **внутри действия**
(`light: { rate: 3 }`, `actions: [{ action: "door", rate: 3 }]`), по умолчанию
6 (1/с). Особенности текущей реализации: `rate` на уровне привязки код не
читает (хотя `SPEC.md` описывает его как поле привязки), а `rotate` своё
сглаживание не настраивает — там внутренний коэффициент.

### 4.3 Условия

Условия используются в `colors`, `conditions`, `hide`/`hideWhen`/`showWhen`,
`light.on`, `rotate.on`, `door.open` и проверяются функцией
`matchesCondition(condition, state, numeric)`:

| Запись | Смысл |
|---|---|
| `"on"` | Состояние ровно `on` (регистр не важен). |
| `"!off"` | Любое состояние, кроме `off`. |
| `">50"`, `">=50"`, `"<10"`, `"<=10"`, `"==100"`, `"!=0"` | Числовое сравнение состояния (или значения привязки, если оно уже число). |
| `"/^heat/"` | Регулярное выражение по состоянию. |
| `true` (только в `hide`) | Синоним `["off", "closed", "unavailable", "unknown"]`. |

Несколько условий задаются таблицей (`"colors": { ">=30": "#f00", "<20": "#0af" }`)
или списком `conditions`; срабатывает первое совпавшее. Если не совпало ничего
и `restore` не `false`, объект плавно возвращается к цвету из файла модели.

### 4.4 Действия и их поведение во времени

| Действие | Что меняет | Как ведёт себя во времени |
|---|---|---|
| `color` | `material.color` всех материалов объекта (без дублей) | Экспоненциальное сглаживание: `c.lerp(target, 1 − e^(−rate·dt))`; базовый цвет берётся из файла модели (`userData._baseColor`) и служит точкой возврата. Есть градиент по числу: `scale: { from: {min,max}, colors: [...] }`. |
| `hide` | `visible` объекта и всех детей | Мгновенно (без анимации), при смене целевого состояния. |
| `light` | Интенсивность `PointLight` + `emissive` материала | Плавно: `ease(current, target, rate, dt)`. Максимум интенсивности = `lumens / 1000` (не меньше 0.05). `emissive` подмешивается пропорционально текущей интенсивности, поэтому объект «светится» даже при общем свете. |
| `rotate` | Вращение объекта вокруг оси | Плавный разгон и торможение (внутренний `ease` с коэффициентом 2), затем `rotateOnAxis`. Ось — `x`/`y`/`z`, скорость — `round_per_second` (или `rps`), направление — `direction: "reverse"`. |
| `door` | Поворот (или сдвиг) створки | Прогресс 0…1 сглаживается `ease(progress, target, rate, dt)`; угол = `degrees` (90 по умолчанию) × прогресс. Каждый кадр трансформация восстанавливается из базовой (`_basePosition`, `_baseQuaternion`) и поворачивается вокруг точки подвеса, вычисленной по габаритам объекта (`hinge`: `left`/`right`/`top`/`bottom`). `slide: true` + `span` — сдвиг вместо поворота. |
| `text` | Спрайт-подпись над объектом | Перерисовывается только при смене текста. Шаблон с подстановками `{state}`, `{value}`, `{name}`, `{unit}`, `{entity}`; `digits` — знаков после запятой, `prefix` — постоянный префикс. |

### 4.5 Свет и подписи, которые создаёт движок

* **Источник света** создаётся один раз на правило `light`:
  `new PointLight(color, 0, distance, decay)`; позиция — центр габаритов
  объекта, пересчитанный в систему координат родителя (иначе автоцентровка
  модели сдвинула бы источник), плюс `offset`; `castShadow` по умолчанию
  выключен. Включение меняет интенсивность от 0 до максимума (`lumens / 1000`).
  Яркость как доля учитывается через `valueMax` и числовое `value`; поле
  `useBrightness` рассчитано на `info.brightness`, которого карточка сейчас не
  передаёт (`bindingView()` отдаёт `state` и `value`).
* **Подпись** — спрайт из `ctx.makeLabel(...)`, ставится над объектом
  (центр габаритов + половина высоты + `elevation`, по умолчанию 0.15).
  Размер — `scale` (0.0035 по умолчанию), шрифт и фон рисует карточка.

### 4.6 Состояния, кадры и «грязные» правила

```
карточка: hass → bus → _syncFromStates() → handle.applyState(key, info)
                                        → ruleEngine.setEntity(key, info)   // помечает правила dirty
кадр:     handle.frame(dt) → computeRule() для dirty → applyRule() для всех
```

Состояние применяется не в момент прихода `hass`, а в следующем кадре: правило
помечается «грязным», цель пересчитывается, затем значение подводится к цели.
`info` содержит `{ key, name, entity, state, value, available }`; недоступная
сущность (`unavailable`/`unknown`) считается «выключено» для `light`/`rotate`
и «закрыто» для `door`.

### 4.7 `dispose`

Движок удаляет только то, что создал сам: спрайты подписей (вместе с
материалом и текстурой) и источники света. Геометрии и материалы модели не
освобождаются — они лежат в общем кэше `geometry.js` и переиспользуются
следующей сценой (`clearGeometryCache()` — сброс кэша в тестах). Собственные
копии материалов, сделанные при клонировании модели, освобождает
`handle.dispose()` из `object-model.js`.

### 4.8 Диагностика из кода

```js
const card = document.querySelector("threejs-3d-card");
const handle = card._engine._modelHandle;
handle.ruleEngine.objectNames();  // имена объектов модели (и алиасы в нижнем регистре)
handle.ruleEngine.describe();     // [{ entityKey, targets, actions }]
card._engine.diagnostics();       // проверка привязок, предупреждения, журнал модели
```

## 5. Чем это отличается от floor3d-card

Сравнение сделано по исходникам floor3d-card (файлы `src_floor3d-card.ts`,
`src_helpers.ts`, `src_types.ts`, `README.md`, `ExportHASS_OBJWriter.java`).

| Свойство | threejs-3d-card (наш формат) | floor3d-card |
|---|---|---|
| **Адресация объектов** | Точное имя, `Шаблон_*`, `/регексп/`, `@группа`, массив имён; поиск по всему дереву | Только точное имя: `this._scene.getObjectByName(element.object_id)` (`src_floor3d-card.ts:1802`). Множества — заранее перечисленные `object_groups`, подставляемые как `<ИмяГруппы>` (`src_helpers.ts:103-140`). Масок, регулярок и групп «по условию» нет |
| **Условия состояния** | `on`, `!off`, `>50`, `>=`, `<=`, `==`, `!=`, `/регексп/` | Только равенство: `if (this._states[index] == item.colorcondition[i].state)` (`src_floor3d-card.ts:3067`, `3093`) |
| **Единицы и масштаб** | Декларативно в описании модели: `source.scale: 0.01` (модели Sweet Home 3D — сантиметры), `source.fitSize`, `center`, `ground` | Поля масштаба в конфигурации карточки нет (`src_types.ts`), модель используется в тех единицах, в которых экспортирована |
| **Форма описания** | Данные (JSON) + обёртка-модуль; при нехватке выразительности — свой код через `create(ctx)` (`docs/MODEL_API.md`) | Конфигурация Lovelace (YAML) + файл модели; точки расширения кодом нет (в карточке нет импорта пользовательских модулей) |
| **Мелочи, влияющие на работу** | Автоустановка камеры по габаритам модели, диагностика привязок с предупреждением о ненайденных объектах, валидатор спецификации, сглаживание реакций | Настройка видов/камер вручную; проверка имён — только косвенная |

## 6. Ограничения и известные расхождения

1. **Единицы — метры** (как в three.js). Сантиметровые модели (Sweet Home 3D,
   часть экспортов Blender) требуют `source.scale: 0.01`.
2. **Без `entities` в конфигурации карточки привязки не работают**: `entity`
   в спецификации — это ключ поля, значение выбирает пользователь
   (`normalizeConfig`, `src/core/bindings.js`).
3. **Имена объектов должны быть уникальны** — см. `docs/OBJECT_NAMES.md`.
4. **Не указывайте `manifest.host: "external"` в объектной модели.** В этом
   режиме карточка считает, что рендерер создаёт сама модель: она не создаёт
   `WebGLRenderer` (`scene.js:203`, `:223-230`) и в `_frame()` выходит сразу
   после `handle.frame(dt)` (`scene.js:618-623`), поэтому сцена остаётся пустой
   (измерено: «вызовов отрисовки WebGL: 0»). `createObjectModel` возвращает
   `external: false`, и объектную модель рисует карточка — это правильный режим.
   Своя отрисовка нужна только моделям-модулям, которые сами создают рендерер и
   отдают его через `ctx.setRenderer` (`models/water-tank/scene.js:135`).
5. **Точка подвеса двери** вычисляется по габаритам объекта, а не берётся из
   файла модели: у створки, чья геометрия далеко от её начала координат, ход
   двери может отличаться от ожидаемого. Проверяйте `door` на своей модели:
   самопроверка `dev/probe-glb.html` печатает смещение и кватернион створки до и
   после открытия.

Значения по п. 4–5 получены самопроверками `dev/probe-glb.html` и
`dev/probe-gltf.html` (отчёты `dev/report-glb.json`, `dev/report-gltf.json`),
которые прогоняются в headless-браузере на стенде `npm run serve`.
