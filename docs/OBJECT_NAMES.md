# Имена объектов модели

Спецификация объектной модели связывает сущности Home Assistant с объектами
модели **по имени**: `target` в `bindings` — это имя объекта внутри файла
модели. Опечатка в имени выглядит как «модель загрузилась, но ничего не
работает»: карточка не найдёт объект, напишет предупреждение в диагностику
и пропустит правило.

Формат спецификации целиком — `skills/threejs-3d-model/reference/SPEC.md`,
техническое описание движка — `docs/OBJECT_MODEL.md`.

---

## 1. Универсальный способ: консоль браузера

Работает для любого формата (OBJ, glTF, GLB) и не зависит от того, чем сделан
файл. Откройте страницу с карточкой, нажмите F12 → Console и выполните:

```js
const engine = document.querySelector("threejs-3d-card")._engine;
engine._modelHandle.root.traverse((n) => { if (n.name) console.log(n.name); });
```

Карточка должна быть уже построена (модель загружена) — иначе `_engine` равен
`null`. Если сцена пустая, включите в конфигурации карточки `show_diagnostics:
true`: карточка покажет собственный список привязок, предупреждений об
объектах, которых нет в модели, и журнал загрузки.

Второй фрагмент показывает модель глазами движка правил — полезно, когда надо
понять, почему правило не сработало:

```js
const handle = document.querySelector("threejs-3d-card")._engine._modelHandle;
console.log(handle.ruleEngine.objectNames());  // все имена (и алиасы в нижнем регистре)
console.table(handle.ruleEngine.describe());   // entity → target → действия
```

`objectNames()` печатает имена дважды: как в файле и в нижнем регистре —
движок ищет объекты без учёта регистра, поэтому в списке есть `Lamp_Kitchen`
и `lamp_kitchen`. В спецификацию пишите имя так, как оно записано в файле.

Оба фрагмента — тот же путь доступа, которым пользуются страницы самопроверки
`dev/probe-glb.html` и `dev/probe-gltf.html`.

## 2. Blender

* **Посмотреть имена:** панель **Scene Collection** (Outliner) справа сверху —
  это и есть имена объектов. Переименование: двойной клик по имени (или F2).
* **Экспорт в OBJ:** `File → Export → Wavefront (.obj)`. При группировке по
  объектам (`Grouping: Object`) экспортёр пишет по группе на каждый объект:
  `o <Имя>`. Загрузчик OBJ в карточке читает и `o`, и `g` — имя берётся из
  любой из этих строк.
* **Экспорт в glTF/GLB:** имена объектов становятся именами узлов (nodes) и
  доступны спецификации как обычные `target`. Пустые объекты (Empty) тоже
  становятся узлами — их имена лучше не использовать как управляемые детали.
* Blender добавляет суффиксы дубликатам (`Lamp_Kitchen.001`). Точка в glTF
  имени вырезается загрузчиком, а в спецификации такое имя придётся указывать
  как есть — проще переименовать объект.

## 3. Sweet Home 3D

* Имена формирует плагин **ExportToHASS** (github.com/adizanni/ExportToHASS,
  ставится файлом `.sh3p`) — именно его используют вместе с floor3d-card.
  Схема имени: префикс уровня плюс имя объекта, то есть `lvl<NNN><Имя объекта>`,
  пробелы заменяются на `_`. В исходнике плагина (`ExportHASS_OBJWriter.java`)
  это шаблон `lvl\d{3}(.*)` и `node.getName().replace(" ", "_")`.
  Пример: мебель «Lamp Kitchen» на первом уровне → `lvl001Lamp_Kitchen`.
* Практический вывод: в спецификации указывайте имя целиком
  (`target: "lvl001Lamp_Kitchen"`) либо работайте масками и группами:
  `target: "lvl001*"` — весь первый уровень, `target: "/^lvl002Lamp_/"`
  — все лампы второго уровня.
* Автор floor3d-card предупреждает в своём README: при удалении объектов из
  модели идентификаторы переназначаются, и после повторного экспорта привязки
  приходится проверять заново. То же верно и для нас — после переэкспорта
  прогоните спецификацию валидатором и проверьте диагностику карточки.

## 4. Требования к именам

| Требование | Почему |
|---|---|
| **Уникальность** во всём дереве модели | Точное имя ищется по индексу «имя → объект», и при дубликате победит последний найденный при обходе. Маски и регулярки вернут все совпадения — правило применится к обоим объектам, что почти всегда не то, чего ждут. |
| **Латиница, цифры, `_`, `-`** | Имена попадают в JSON-спецификацию, в шаблоны и в диагностику. Пробелы в OBJ формально допустимы, но в glTF three.js заменяет их на `_`, а символы `[ ] . : /` вырезает (`PropertyBinding.sanitizeNodeName`) — имя в файле и в сцене перестанут совпадать. |
| **Схема `<Тип>_<Место>`** | `Lamp_Kitchen`, `Door_Front`, `Fan_Bathroom`, `Sensor_Temp`, `Window_Living`, `Device_Press`, `Label_Temp`. Тогда шаблоны вида `Lamp_*` и группы `@lights` собираются сами. |
| **Отдельный объект на каждую управляемую деталь** | Створка двери не должна быть частью группы со всей стеной: повернуть можно только объект целиком. Петля/рама — отдельный объект, если её тоже надо двигать. |
| **Имя на нужном уровне дерева** | Движок обходит всё дерево (`traverse`), поэтому вложенность не важна. Важна уникальность: дочерний объект с именем, как у родителя, сделает `target` неоднозначным. |

## 5. Если имена менять нельзя

Файл модели часто чужой (заводской экспорт, архив производителя) — переименовывать
объекты в нём не нужно. Спецификация умеет адресовать объекты и без точного имени:

```json
{
  "groups": {
    "lights":   ["Lamp_Kitchen", "Lamp_Hall"],
    "windows":  ["/^Window_/"],
    "level2":   ["lvl002*"]
  },
  "bindings": [
    { "entity": "light.all", "target": "@lights" },
    { "entity": "binary_sensor.window_any", "target": "@windows", "colors": { "on": "#8ecbff" } },
    { "entity": "light.floor2", "target": "/^lvl002Lamp_/" }
  ]
}
```

Подробности адресации (точное имя, `Шаблон_*`, `/регексп/`, `@группа`, массив
имён) — в `docs/OBJECT_MODEL.md` и `reference/SPEC.md`.
