# Создание 3D-модели для threejs-3d-card

Ты создаёшь **модель** — файл-описание, который карточка `threejs-3d-card`
загружает и связывает с Home Assistant. Пользователь получает работающую
карточку без программирования.

## Что ты должен выдать

Обязателен один артефакт, остальные — по необходимости:

1. **`<id>-model.json`** — спецификация: где взять файл модели и что с чем
   связать. Карточка загружает её **без обёртки**: `model: /local/3d/<id>-model.json`
   либо `model: asset:<id>-model.json`, если файл загружен в редакторе
   карточки (см. `reference/SPEC.md`, §3).
2. **`<id>-model.js`** — обёртка на 3–8 строк — только когда спецификации
   не хватает (свой код через `create(ctx)`, см. `reference/SPEC.md`,
   раздел «Расширение кодом»).
3. *(если у пользователя нет готового 3D-файла)* — **`<id>-model.obj`** —
   простая модель, сгенерированная кодом (см. «Модель с нуля»). Если нужны
   `rotate` или распашная дверь — вместо OBJ собирается **`.glb`** (структура —
   по образцу `examples/hinged-door.glb`).

Плюс короткая инструкция: куда положить файлы, что вписать в карточку.

## Порядок работы

1. **Уточни у пользователя только то, без чего нельзя начать:**
   * есть ли готовый файл модели (OBJ/MTL или GLB) и по какому он URL;
   * какие сущности Home Assistant должны на неё влиять (список `entity_id`);
   * что должно происходить: цвет, скрытие, свет, вращение, дверь, текст.
   Если нужно вращение детали или распашная дверь, а файл — OBJ, сразу
   предупреди, что понадобится GLB (см. «Формат файла: OBJ или GLB»).
   Если данных нет — сделай разумное предположение, явно его назови и продолжай.
   Не задавай больше трёх вопросов подряд.

2. **Определи имена объектов модели.** Это самое важное:
   * у готового файла — попроси пользователя выполнить в консоли браузера
     на странице с моделью фрагмент из `docs/OBJECT_NAMES.md`, либо используй
     имена, которые он назвал;
   * при генерации модели с нуля имена придумываешь ты — придерживайся схемы
     `<Тип>_<Место>`: `Lamp_Kitchen`, `Door_Front`, `Fan_Bathroom`, `Sensor_Temp`.
   Имена должны быть **уникальны** и состоять из латиницы, цифр, `_` и `-`.

3. **Собери спецификацию** строго по `reference/SPEC.md`. Не выдумывай поля:
   всё, чего нет в справочнике, карточка проигнорирует. Если в glTF/GLB-файле
   есть пометки `t3d*` (кастомные свойства Blender, рецепт — в
   `docs/OBJECT_NAMES.md` §2), полный список привязок писать не нужно:
   достаточно минимальной спецификации с `bindingsFrom: { gltfExtras: true }` —
   карточка прочитает привязки из пометок в самом файле.

4. **Проверь спецификацию двумя скриптами** (обязательно):
   ```
   node skills/threejs-3d-model/scripts/validate-model.mjs путь/к/<id>-model.json
   node skills/threejs-3d-model/scripts/check-targets.mjs путь/к/<id>-model.json
   ```
   `validate-model.mjs` ловит опечатки в действиях, пустые `target`,
   несовпадение `entity` с `entityConfig`, отсутствующие поля.
   `check-targets.mjs` сверяет каждый `target` с **реальным файлом модели**
   (группы `o <Имя>` в OBJ, имена узлов в GLB/glTF) и печатает, сколько
   объектов управляется и сколько осталось статичными. Исправляй до нуля
   ошибок и предупреждений (у `check-targets` — до кода возврата 0).

5. **Отдай результат** в виде готовых файлов и точной конфигурации карточки.

## Жёсткие правила

* `entity` — это **ключ привязки**, и он же `entity_id` Home Assistant.
  Значение по умолчанию для привязки пользователь выбирает в редакторе
  карточки; в спецификации укажи `entity` как ожидаемый `entity_id`.
* `target` — имя объекта **внутри файла модели**. Точное имя, `Шаблон_*`,
  `/регулярка/` или `@группа`. Регистр не важен.
* **Жёсткие группы.** Всё, что движется как одна деталь, должно попадать в одно
  действие:
  * петлевая (распашная) дверь — ручка, стекло, наклейка должны быть **частью
    того же объекта**, что и створка: точка подвеса считается по габариту
    каждого объекта, поэтому отдельная ручка повернётся вокруг собственного
    края (в OBJ части двери — одна группа `o Door_<Место>`, а не три);
  * сдвиг (`door.slide`) можно задавать несколькими объектами — они едут на одну
    величину `span` (проверено: три объекта сместились синхронно на 0.500 м,
    при совпадающих габаритах и точке подвеса);
  * детали, которые едут или вращаются вместе (оснастка на столе, болты,
    стружка), перечисляйте в одном `target: ["A", "B"]` или через `groups` +
    `target: "@имя"`: объекты, не попавшие в `target`, останутся на месте.
* Одно действие — один ключ внутри привязки: `colors`, `hide`, `light`,
  `rotate`, `door`, `text`, `play`. Для нескольких действий используй
  `actions: [...]`.
* Единицы измерения — **метры** (как в three.js). Если модель в сантиметрах,
  укажи `source.scale: 0.01`. Модели из Sweet Home 3D — сантиметры.
* Не пиши в спецификацию JavaScript: она должна оставаться данными (JSON).
  Логика, которой не хватает, оформляется отдельным `*.js`-модулем модели
  (см. `reference/SPEC.md`, раздел «Расширение кодом»).
* Не ссылайся на объекты, которых нет в модели: валидатор предупредит,
  а карточка покажет предупреждение в диагностике.

## Что делать в типовых случаях

| Просьба пользователя | Решение |
|---|---|
| «Лампа должна светиться» | привязка с `light: { lumens: 800 }` + `colors: { on: "#ffd9a0", off: "#3a3a3a" }` |
| «Показывать, открыта ли дверь» | сдвиг створки: `door: { slide: true, axis: "x", span: 0.9, open: ["on"] }` (петлю `hinge`/`degrees` в 0.1.3 не советуем — см. ниже) |
| «Вентилятор должен крутиться» | `rotate: { axis: "y", round_per_second: 2 }` — модель при этом должна быть GLB (в OBJ деталь уедет, см. ниже) |
| «Скрыть объект, когда выключено» | `hide: ["off", "closed"]` |
| «Показать температуру на модели» | `text: { template: "{value} {unit}" }` |
| «Цвет по уровню» | `scale: { from: { min: 0, max: 100 }, colors: ["#00ff00","#ffff00","#ff0000"] }` |
| «Несколько деталей на одну сущность» | `target: ["Lamp_1", "Lamp_2"]` или `groups` + `target: "@lamps"` |
| Модель слишком большая/маленькая | `source: { scale: 0.01 }` или `source: { fitSize: 20 }` |
| Модель «висит в воздухе» | `source: { center: true, ground: true }` (по умолчанию включено) |
| «Анимация из Blender запускается по состоянию» | `play: { clip: "<имя клипа>", on: ["on"] }` — клип и объекты в Blender должны быть названы (см. `reference/SPEC.md` §6.7) |
| «Спецификация не нужна, если пометки есть в файле» | минимальная спека (manifest + source + `bindingsFrom: { gltfExtras: true }`) — список привязок не пишется: карточка читает их из пометок `t3d*` в glTF/GLB (рецепт Blender — `docs/OBJECT_NAMES.md` §2) |

Из строки про дверь есть исключение, и оно важное: **петля (`hinge` + `degrees`)
в версии 0.1.3 смещает створку** — в закрытом положении на `2 × (pivot −
position)`, то есть на удвоенное расстояние от объекта до точки подвеса (см.
«Известные расхождения» в `README.md` скилла и
`src/core/object-rules.js:503–508`; замер на модели станка — 0,500 м при ширине
створки 1,0 м). Пока это не исправлено в ядре, распашную дверь показывайте
сдвигом — `door: { slide: true, axis: "x", span: <ширина створки> }`, либо честно
предупредите пользователя о смещении.

## Формат файла: OBJ или GLB

Карточка работает с моделью как glTF-загрузчик: у каждого объекта есть своя
локальная геометрия и своя позиция. В OBJ это не так — там позиция у всех
объектов `(0, 0, 0)`, а координаты вершин мировые. Поэтому от формата зависит,
какие действия работают:

| Действие | OBJ | glTF/GLB |
|---|---|---|
| `hide`, `colors`, `light`, `text` | да | да |
| `door: { slide: true, … }` (сдвиг) | да — объекты едут на одну величину `span` | да |
| `rotate` | **нет**: объект вращается вокруг начала координат сцены, а не вокруг своей оси | да — у каждого узла своё `translation`, вершины локальные |
| `door` с петлёй (`hinge` + `degrees`) | смещает створку (0.1.3) | смещает створку (0.1.3) |
| `play` (клипы) | клипов в OBJ нет | да |

Оговорка к «да» в строке `door.slide`: `prepareHinge` вызывается и при сдвиге
(`src/core/object-rules.js:420`), поэтому створка сначала смещается, и только
потом едет на `span` — подробности в `reference/SPEC.md` §6.5.

Правило выбора:

* **OBJ** — когда нужны только `hide`, `colors`, `light`, `text` и `door.slide`.
  Плюс: это обычный текст, его можно сгенерировать кодом.
* **glTF/GLB** — когда нужны `rotate` (вентилятор, ротор) или честная
  распашная дверь. Просите файл из Blender (или экспорт OBJ → Blender → GLB),
  где **каждая деталь — отдельный узел** со своим `translation`, а вершины
  локальные. Готовый образец такой структуры — `examples/hinged-door.glb`
  (и спецификация `examples/hinged-door.json`).

## Модель с нуля

Если готового файла нет — сгенерируй OBJ программно: это обычный текст.
OBJ подходит для `hide`, `colors`, `light`, `text` и `door.slide`; если нужны
`rotate` или распашная дверь — см. развилку в разделе «Формат файла» выше,
нужен GLB.
Минимальный OBJ с двумя объектами (пол и лампа):

```
# <id> — модель для threejs-3d-card
o Floor
v 0 0 0
v 4 0 0
v 4 0 3
v 0 0 3
f 1 2 3
f 1 3 4

o Lamp_Ceiling
v 1.8 2.4 1.4
v 2.2 2.4 1.4
v 2.2 2.6 1.6
v 1.8 2.6 1.6
f 1 2 3
f 1 3 4
```

Правила генерации:
* каждый управляемый объект — отдельная группа `o <Имя>`;
* координаты в метрах, Y — вверх, объект стоит на `y = 0`;
* **обязательно** строка `mtllib <файл>.mtl` в начале и `usemtl <Имя>`
  перед гранями каждого объекта — без них загрузчик применит белый материал,
  и смена цвета по состоянию будет выглядеть как «белое → белое»;
* в MTL для каждого `newmtl <Имя>` задай базовый цвет `Kd r g b` (например,
  для лампы — тёмный `Kd 0.22 0.22 0.24`): карточка возвращается к этому цвету,
  когда ни одно условие не совпало;
* лампа/светильник — небольшая деталь на высоте потолка;
* дверь — плоский прямоугольник (створка) рядом с полом, высотой ~2 м; ручка,
  стекло и наклейка — **в той же группе** `o Door_<Место>`, что и створка;
* вентилятор/ротор в OBJ не делай: `rotate` в OBJ крутит деталь вокруг начала
  координат сцены, а не вокруг её оси — для вращения нужен GLB;
* не делай модель сложнее 200 строк: её цель — показать работу привязок.

## Примеры

Готовый рабочий пример — в `examples/`:

| Файл | Что это |
|---|---|
| `examples/room.json` | спецификация демо-комнаты (OBJ): лампа, дверь, вентилятор, датчик температуры, подпись |
| `examples/room.js` | обёртка, которая читает `room.json` и отдаёт модель карточке |
| `examples/room.obj` + `examples/room.mtl` | геометрия и материалы (сгенерированы, годятся как образец) |
| `examples/hinged-door.json` + `examples/hinged-door.glb` | образец **glTF/GLB**: узел на объект, у каждого узла свой `translation`, вершины локальные, части створки — дочерние узлы. Пересобирается `scripts/make-example-glb.mjs` |

`room.json` — исторический пример: он относится к версии, где петлёй ещё
пользовались (`door: { hinge: "left", degrees: 95 }`), поэтому он заодно
показывает смещение створки. Для новых моделей берите `hinged-door.*` и
`door.slide`.

Скопируй пример и правь его — это быстрее и надёжнее, чем писать с нуля.

## Чего делать нельзя

* Писать `target` объекта, которого нет в модели (сцена будет пустой без объяснений).
* Использовать `condition` вместо `colors`/`conditions` — такого поля нет.
* Смешивать `door.slide` и `door.degrees`: для сдвига — `slide: true` и
  `span`, для поворота — `degrees` и `hinge`.
* Советовать `rotate` или петлевую дверь на OBJ-модели без оговорки: в OBJ
  вращение идёт вокруг начала координат сцены, а петля (0.1.3) смещает створку
  (см. «Формат файла: OBJ или GLB» и README скилла).
* Обещать, что «всё заработает само»: укажи пользователю точные шаги установки
  (пути файлов и строку конфигурации карточки).
